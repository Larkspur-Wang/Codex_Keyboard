# 01_封面

大家好，我是 Lark。今天带来的案例叫《Codex 任务电台》。它看起来是一把八键小键盘，但我把它改成了四个 Codex 任务的实体入口：可以对任务说话，也可以直接从键盘听任务汇报。

# 02_Lark

我原来做的是嵌入式软件，日常工作离不开硬件、固件和系统边界。后来开始做 AI 产品，我没有把这些经验扔掉，而是继续问一个很朴素的问题：模型很强，但怎样才能真正进入每天的工作？这把键盘就是其中一次回答。

# 03_20秒看懂

先不讲技术，我用二十秒把结果说清楚。按住上排键，对一个 Codex 任务说要求；松开以后，Codex 在后台工作。任务完成后，对应的灯亮。再按一下下排键，键盘就把刚完成的内容读给我听。

# 04_一句话定义

一句话定义它：把四个 Codex 任务，变成四个可说、可听、会亮灯的实体频道。重点不是多做一个通知屏，也不是做一个更复杂的快捷键，而是少看一点屏幕。

# 05_真实工作桌面

这个想法来自我的真实工作。我经常同时开着几个 Codex 任务：一个改固件，一个做 App，一个跑测试，还有一个整理文档。它们都能并行，但我会不断切窗口，看谁做完了、谁在等我，注意力就这样被切碎了。

# 06_三个麻烦

我后来把麻烦归成三件事。第一，很多粗粒度要求明明说一句就够了，却必须坐回电脑前打字。第二，我总在切窗口。第三，我总想知道结果出来没有，于是本来能离开的时间，还是守在屏幕旁边。

# 07_调度瓶颈

AI 可以同时跑四个任务，人却只有一双手。真正卡住我的，不是模型写代码的速度，而是下要求、看状态、收结果这几件小事。每件事都不难，但一天做几十次，就很打断工作。

# 08_灵感瞬间

这时我手边正好有一块 EasyInput V2。它有八个键、五颗灯、麦克风、Wi-Fi、PSRAM，也留了扬声器链路。八个键刚好可以分成上下两排：上排说，下排听。于是它不再只是一把快捷键键盘，而是一个四频道任务对讲机。

# 09_四个频道

我用了对讲机这个比喻，因为它很容易理解。四个任务就是四个频道。对哪个频道说，要求就进入哪个任务；哪个频道有回信，就亮哪颗灯；想听哪个频道，就按对应的下排键。

# 10_交互草图

这是最初的交互草图，最后基本没变。S1 到 S4 负责按住说话，S5 到 S8 负责收听。左起四颗灯分别对应四个槽位，第五颗灯不参与信箱。这里最重要的是一一对应，用户不用记菜单，也不用切模式。

# 11_开发板本质

EasyInput 出厂时可以直接当 AI 键盘使用，但它的本质是一块开发板。键位和旋钮只是已经做好的一个形态。真正有意思的是，你可以重新定义这块板怎样感知人、怎样和电脑协作、怎样给反馈。

# 12_用人话认识硬件

不用先记芯片型号，先用人话认识它。八个机械键让它能按，旋钮让它能转，I2S 麦克风让它能听，功放和扬声器让它能说，五颗 RGB 灯让它能安静地提示状态。USB、蓝牙和 Wi-Fi 则负责把它接到电脑上。

# 13_激活能力

这次案例真正用上了几项原来没有完整跑起来的能力。PSRAM 用来放音频缓冲，Wi-Fi 负责传声音，数字功放和扬声器负责把总结播出来。也就是说，我们不是只改键位配置，而是把整条音频链路做进了固件。

# 14_本地WiFi

第一版我先选择同一个局域网。键盘和 Mac 连到同一个 Wi-Fi，声音和状态都直接走本地链路。这样问题更容易定位，数据也更可控。标题里的“远程开发”，指的是人可以离开 Codex 窗口继续工作，不是说当前版本已经能从公网遥控家里的 Mac。

# 15_MacApp绑定

Mac App 是这套系统的管家。它把四个槽分别绑定到四个 Codex 任务，也显示哪些槽有未听汇报、键盘是否在线。这里展示的是实际界面，任务名称已经换成课程示例。底层数据库只由 Host 管理，界面通过 Host 读取状态，避免两边同时改数据。

# 16_按住说

输入动作很简单。按住 S1 到 S4 中的一个键，键盘开始录音；直接说要求；松开以后结束录音。Mac 调用千问 ASR 把语音转成文字，再把文字排进对应 Codex 任务的队列里。

# 17_后台工作

最有价值的动作其实是“发完就走”。我不需要看进度条，也不用等一段命令跑完。Codex 在后台做事，我可以去处理别的工作。只有任务真的完成，系统才来提醒我。

# 18_语音信箱灯

任务完成后，对应槽位就像收到一封语音信。左起四颗灯分别对应四个槽；未听内容越多，亮度越高。第五颗灯保持不用，避免把四槽逻辑搞乱。灯光的作用不是吸引注意，而是让我路过时一眼知道哪里有新结果。

# 19_收听映射

上下两排是一一配对的。S1 负责给槽一说话，S5 负责听槽一；S2 对 S6，S3 对 S7，S4 对 S8。按一下下排键，就播放那个槽提前生成好的音频，不需要再临时等待总结。

# 20_总架构

整套架构可以不用协议名来解释。键盘是身体，负责收声音、亮灯、播声音；Mac 是管家，负责绑定、监控、总结和缓存；Codex 是执行者，真正写代码、改文件、跑测试。三边分工清楚，后面排错才不会乱。

# 21_说进去

语音输入这条链是这样的。键盘采集十六千赫兹单声道 PCM，通过局域网送到 Mac。Mac 调用北京区 DashScope 的千问语音识别，把声音变成文字，再把文字放进绑定任务。键盘不需要理解内容，它只要把声音可靠送到就行。

# 22_Spark总结

任务完成以后，Host 读取助手最后的回复，再交给本地 Codex Spark 提炼。这里我特意限制了来源：只看真正完成时的助手回复，不把调试过程、工具日志和中间想法念出来。总结要回答三件事：完成了什么、结果怎样、还剩什么。

# 23_听回来

总结完成后，Mac 调用千问 TTS 生成中文女声，并加密缓存到本地。按下播放键后，键盘通过局域网取回对应音频，再交给 I2S 扬声器播放。缓存提前生成，所以按键后可以更快出声；传输部分也按流式播放方向优化。

# 24_真正听过

这里有一个很容易写错的细节。音频包传完，不代表声音已经播完。如果这时就熄灯和删缓存，最后一段可能还没真正听到。我们的规则是：扬声器确认播放结束以后，才标记为听过、熄灯并删除那一条缓存。

# 25_抽取工程

这个案例不是在原键盘仓库里不断加特殊代码。我先从成熟的 EasyInput 固件基线中，抽出本地 Wi-Fi 版本需要的部分，建立独立的 Codex_Keyboard 仓库。里面明确分成 firmware 和 app，两边的边界、协议和测试都单独记录，原仓库保持不动。

# 26_第一次卡住

开发过程并不顺。第一个问题是下载模式很难进，串口设备只在上电瞬间出现。最后固定的方法是先用 debug reset 拉住，再抓断电上电的瞬间。另一个问题更迷惑：有开机音，却没有任务音频。开机音只证明扬声器能响，不能证明网络、缓存和解码都通，所以必须逐段排查。

# 27_隐蔽问题

后来还有三类更隐蔽的问题。传输窗口大过设备的 UDP 接收队列，导致丢包和重传，听起来就是每次都很慢。灯带在 PCB 正面看是从左到右，但数据链路方向相反，所以灯序一开始完全反了。S3、S4 不亮，则是旧 TTS 状态卡住队列，新完成内容进不来。

# 28_怎样算好了

这个项目让我反复提醒自己：测试绿了，不等于真机通过。代码检查只能证明结构，自动化测试证明函数和协议，运行日志证明包到过。最后还要真实按键、看灯、听声音，再确认播放结束后灯真的熄灭。人的耳朵和手，仍然是最后一道验收。

# 29_还能改成什么

同一块板还可以改成很多东西，比如会议任务遥控器、工位语音信箱、设备调试台，或者家庭自动化控制台。不过我更建议从问题出发：先找一个每天都在重复、总打断你的动作，再决定它应该长成什么硬件。

# 30_收束

最后我想留下一个很具体的认识。AI 硬件不是把大模型塞进 ESP32，而是给 AI 一副能进入日常工作的身体。它能听见要求，安静地等结果，再用灯和声音把重要的事带回来。这就是 Codex 任务电台。

# 31_附录硬件参数

附录先列公开硬件参数。主控是 ESP32-S3R8，带八兆 PSRAM，外置十六兆 Flash；有八个机械键、一个旋钮、五颗 WS2812、I2S 麦克风、数字功放和扬声器接口，同时支持 USB-C、蓝牙和二点四 GHz Wi-Fi。

# 32_附录GPIO

这是 V2 板正面丝印和 GPIO 的最终对照。上排 S1、S2、S3、S4 分别是 GPIO2、47、38、41；下排 S5、S6、S7、S8 分别是 GPIO1、6、7、48。排查键位时要看丝印和运行诊断，不能根据最终功能猜 GPIO。

# 33_附录输入时序

完整输入时序从按键按下开始。Host 发出开始采集控制，键盘持续上传 EIAU 音频帧；松开后结束并整理音频。Host 调用 Qwen ASR，拿到文本，再写进对应任务的 FIFO。每一步都有明确的会话代际，避免旧连接的数据混进新录音。

# 34_附录输出时序

输出侧从 Codex 完成事件开始。Spark 先整理可听总结，Qwen TTS 生成音频并缓存，灯亮等待用户。播放时，传输完成和扬声器完成分开记录；只有扬声器完成，才标记 heard、熄灯和删除缓存。任何一步失败，都保留未听状态。

# 35_附录安全

密钥只存在 Mac 本地的 `.env`，权限设为 0600，并由 Git 忽略。摘要状态在 Host 管理的 SQLite 中，音频加密缓存到 Mac，听完后删除。键盘只保存连接所需配置，运行时只认槽位号，不保存 Codex 对话。

# 36_附录仓库

完整工程在公开仓库 Larkspur-Wang/Codex_Keyboard。firmware 目录是 ESP-IDF 设备端，app 目录包含 Rust Host 和 Dashboard，docs 记录产品、架构、协议与开发过程。建议先按 README 跑同 Wi-Fi 演示，再深入看测试和协议。
