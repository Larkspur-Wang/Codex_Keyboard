# 01_封面

大家好，我是 Lark。今天带来的案例叫《Codex 任务电台》。它看起来是一把八键小键盘，但我把它改成了四个 Codex 任务的实体入口：可以对任务说话，也可以直接从键盘听任务汇报。

# 02_Lark

我是 Lark，从嵌入式软件转向 AI 产品工作。这次案例同时涉及固件、电脑端软件和模型服务，我会沿着实际操作来讲：从为什么想做，到怎样跑通，再到出了问题怎么查。

# 03_20秒看懂

先看操作。按住上排键，对一个 Codex 任务说要求；松开以后，识别出的文字排进对应任务。任务完成，且总结音频准备好后，对应的灯亮。再按一下下排键，键盘就播放这次结果。

# 04_一句话定义

四个槽分别对应四个 Codex 任务。常用要求可以直接说，结果可以按需听；需要检查代码或处理授权时，仍然回到电脑。

# 05_真实工作桌面

这个想法来自我的真实工作。我经常同时开着几个 Codex 任务：一个改固件，一个做 App，一个跑测试，还有一个整理文档。它们都能并行，但我会不断切窗口，看谁做完了、谁在等我，注意力就这样被切碎了。

# 06_三个麻烦

我后来把麻烦归成三件事。第一，很多粗粒度要求明明说一句就够了，却必须坐回电脑前打字。第二，我总在切窗口。第三，我总想知道结果出来没有，于是本来能离开的时间，还是守在屏幕旁边。

# 07_调度瓶颈

AI 可以同时跑四个任务，人却只有一双手。真正卡住我的，不是模型写代码的速度，而是下要求、看状态、收结果这几件小事。每件事都不难，但一天做几十次，就很打断工作。

# 08_灵感瞬间

这时我手边正好有一块 EasyInput V2。它有八个键、五颗灯、麦克风、Wi-Fi、PSRAM，也留了扬声器链路。八个键刚好可以分成上下两排：上排说，下排听。于是它不再只是一把快捷键键盘，而是一个四频道任务对讲机。

# 09_四个频道

我用了对讲机这个比喻，因为它很容易理解。四个任务就是四个频道。对哪个频道说，要求就进入哪个任务；哪个频道有回信，就亮哪颗灯；想听哪个频道，就按对应的下排键。

# 10_交互草图

这是最初的交互草图，主体没有变。S1 到 S4 负责按住说话，S5 到 S8 负责收听。左起四颗灯一一对应四个语音信箱，最右第五颗单独显示后台有几个任务正在跑。旋钮也没有闲着：逆时针调小键盘扬声器，顺时针调大，短按一下还会直接告诉我现在是百分之多少。

# 11_开发板本质

这里是同一块 EasyInput V2 的实物。课程不需要重新焊一套硬件，而是改固件和电脑端软件：按键从快捷键变成录音和播放入口，旋钮控制板载音量。后面的芯片和接口继续使用。

# 12_用人话认识硬件

不用先记芯片型号，先用人话认识它。八个机械键让它能按，旋钮直接调键盘自己的播报音量，I2S 麦克风让它能听，功放和扬声器让它能说，五颗 RGB 灯让它安静地提示状态。音量做成十档，逆时针减、顺时针加；短按旋钮，键盘会直接播报当前档位。

# 13_激活能力

这两张是实际 PCB 资料图。PSRAM 放音频缓冲，Wi-Fi 和 Mac 传声音，数字功放驱动扬声器。排查没声音时，沿着缓冲、传输、解码和播放逐段看，比先猜是哪颗芯片坏了更有效。

# 14_本地WiFi

第一版我先选择同一个局域网。键盘和 Mac 连到同一个 Wi-Fi，声音和状态都直接走本地链路。这样问题更容易定位，数据也更可控。标题里的“远程开发”，指的是人可以离开 Codex 窗口继续工作，不是说当前版本已经能从公网遥控家里的 Mac。

# 15_MacApp绑定

这是实际 App 的脱敏截图。界面用于选择 Codex 任务、绑定四槽，查看排队数和未听汇报。它没有键盘在线探测字段，Host 正常也不能直接证明设备已连通。数据库只由 Host 管理，界面通过 Host 读取状态。

# 16_按住说

输入动作很简单。按住 S1 到 S4 中的一个键，键盘开始录音；直接说要求；松开以后结束录音。Mac 调用千问 ASR 把语音转成文字，再把文字排进对应 Codex 任务的队列里。

# 17_后台工作

最有价值的动作其实是“发完就走”。我不需要看进度条，也不用等一段命令跑完。Codex 在后台做事，我可以去处理别的工作。只有任务真的完成，系统才来提醒我。

# 18_语音信箱灯

五颗灯现在分成两种职责。左起四颗仍然是四个语音信箱：哪个任务完成了，对应槽位就亮，未听内容越多越亮。最右第五颗只看后台忙碌程度：空闲是绿色，一个任务黄色，两个橙色，三个紫色，四个红色；全部完成后再回到绿色。为了让紫色和红色不是只画在图上，Host 允许四个不同任务同时运行；但同一个任务仍然排队，避免同一段对话同时写入。这样一眼就能分清“还有多少任务在跑”和“哪些结果还没听”。

# 19_收听映射

上下两排是一一配对的。S1 负责给槽一说话，S5 负责听槽一；S2 对 S6，S3 对 S7，S4 对 S8。按一下下排键，就播放那个槽提前生成好的音频，不需要再临时等待总结。

# 20_总架构

分工按这三部分看。键盘收声音、亮灯、播放；Mac 管理绑定和队列，调用模型服务并缓存音频；Codex 执行要求。第五灯也由 Mac 根据真实任务事件计算，固件只显示收到的运行数。

# 21_原理基础篇

接下来十页解释复现时会遇到的名词。每页看一个问题：网络怎么走，配置存在哪，什么情况下才算听完。第一次听不必记协议字段，动手遇到问题时再回来对照。

# 22_局域网直连

先把图里的两段网络分开看。键盘只连接局域网里的 Mac，Mac 再把录音发给 DashScope 识别，调用 Codex 执行任务，最后调用 TTS。我们省掉了键盘和 Mac 之间的公网中继，没有把模型搬到本地。断外网时，新的识别、任务和合成都可能停下来。UDP 是沿用现有音频链的选择，WebSocket 也能用在局域网，不能简单说单片机用不了。

# 23_配网

键盘没有屏幕，连接信息由电脑下发。本课的 provision-lan 命令走 USB HID，保存网络名称、密码、Mac 地址、端口和设备密钥。它收到精确的保存确认后才报告成功，但保存成功还不是连通成功，后面要看心跳和任务状态变化。如果 Mac 的地址变了，也要更新端点。固件有蓝牙管理通道，不代表这个命令会在 USB 失败时自动切蓝牙。

# 24_Flash分区与NVS

这张表按实际地址列出 Flash 内容。NVS 在应用程序前面，保存 Wi-Fi、设备密钥和音量。我们的烧录命令只写引导、分区表和应用，不擦 NVS 及独立音效区。还要注意，十档音量提示音嵌入在应用镜像里，不是在后面的音效分区。保留配置有一个前提：板型和分区布局一致。换布局或整片擦除时，不能沿用这项结论。

# 25_声音变数字

上行每秒有一万六千个采样点，用十六位单声道 PCM 表示。它从数字麦克风经过 I2S 进入固件，再分帧发给 Mac。下行则由 TTS 生成四万八千赫兹的音频，Host 编码成 ADPCM，再加密下发。这里不要混淆认证和加密：上行带 HMAC 校验，不额外隐藏 PCM 内容。声音变快或变尖时，采样率是一个值得先检查的参数，但也不能只凭听感确定原因。

# 26_认证与加密

这两个名词要分开记。HMAC 用来检查来源和数据完整性，内容本身仍可能被读取；AES-GCM 才负责加密音频，同时验证密文。我们对上行 PCM 和控制报文做认证，下行音频与本地缓存使用加密。设备通信密钥和 Mac 缓存密钥也是分开的。排错时要看哪一层校验失败，不要因为都在家里的 Wi-Fi 就跳过检查。

# 27_代际

看这个例子：摘要版本七还没听完，播放到一半断电了。重连后内容仍然是版本七，只是重新建立播放身份 B。上一轮 A 的回执如果迟到了，不能拿它当作 B 已经播完。只有 B 真正完成且身份匹配，Host 才消费这条未读。实际协议还会检查连接编号和租约；不要把摘要版本和连接重建混成一个编号。

# 28_FIFO排队

图里任务一有 A、B、C 三条要求，只有 A 正在执行。其他不同任务可以同时运行，最多四路。第五灯数的是实际运行的任务，不把还在排队的要求算进去，所以这个例子显示紫色。队列是按任务而不是按物理槽划分的：把两个槽都绑定到同一个任务，也只会使用同一条队列。

# 29_任务完成

任务结束和音频就绪是两个时间点。Host 看到 task_complete 后更新运行数，然后取助手最终回复做总结，再调用 TTS。等缓存完整发布，对应信箱灯才亮。所以任务做完后还可能等一会。完成事件也不等于任务成功，最后回复可能是在报告失败或需要人处理的阻碍。摘要没有固定十五秒限制，长度随实际内容变化。

# 30_听过语义

上面一条是收数据，下面一条是播放。收到二十四 KiB 后，键盘就开始解码播放，后续数据继续到达；很短的音频则收完再播。这能减少等待，但网络太慢仍可能卡住或失败。收完数据后也不能立刻删缓存，要等扬声器完成并回传匹配身份的确认。中途断电，灯会灭，但 Host 里的未读记录应保留，重连后再恢复显示。

# 31_常驻管家

App 窗口只负责绑定和显示状态，实际后台进程是 easy-codex-host。它在用户登录后由 LaunchAgent 运行，管理任务观察、SQLite 和缓存文件。关闭窗口不会停掉它，但 Mac 睡眠、退出登录或断网仍会影响工作。要升级后台程序，用 launch-agent-upgrade；只重开窗口不会替换 Host。接下来把这些机制串成输入和播放两条链路。

# 32_说进去

语音输入这条链是这样的。键盘采集十六千赫兹单声道 PCM，通过局域网送到 Mac。Mac 调用北京区 DashScope 的千问语音识别，把声音变成文字，再把文字放进绑定任务。键盘不需要理解内容，它只要把声音可靠送到就行。

# 33_Spark总结

任务完成以后，Host 读取助手最后的回复，再交给隔离运行的 Codex Luna High 提炼。这里我限制的是来源：只看真正完成时的助手回复，不把调试过程、工具日志和中间想法念出来。短结果就说一句，复杂结果才多讲。实践中我也踩过一个坑：给总结加太多字数、证据和内容评分，反而会把本来能听的结果挡住。现在质量交给 Luna，Host 只守结构、任务归属、长度、脱敏和有效音频这些运行底线。

# 34_听回来

总结完成后，Mac 把整段文字一次交给千问 Audio 3.0 TTS Flash，用龙安风玥女声生成一条完整音频，再加密缓存到本地，不做分句拼接。按下播放键后，键盘通过局域网取回对应音频，再交给 I2S 扬声器播放。音频早在任务完成时就已经生成，所以按键不是临时等云端合成。

# 35_抽取工程

来源分两层。最初固件基线来自 easy-input-keyboard；加入 Codex 接入和远程探索的工程是 easy-codex-input。这次实际从后者抽出本地 Wi-Fi 版本，建立 Codex_Keyboard，分成 firmware 和 app。两个来源仓库都保留，不在里面继续加课程专用修改。

# 36_第一次卡住

开发过程并不顺。第一个问题是下载模式很难进，串口设备只在上电瞬间出现。最后固定的方法是先用 debug reset 拉住，再抓断电上电的瞬间。另一个问题更迷惑：有开机音，却没有任务音频。开机音只证明扬声器能响，不能证明网络、缓存和解码都通，所以必须逐段排查。

# 37_隐蔽问题

后来还有三类更隐蔽的问题。传输窗口大过设备的 UDP 接收队列，导致丢包和重传，听起来就是每次都很慢。灯带在 PCB 正面看是从左到右，但数据链路方向相反，所以灯序一开始完全反了。最后一个问题最值得讲：任务和总结其实都完成了，S7 却不亮，因为我给 Luna 输出叠了太多自以为安全的内容门禁。解决办法不是继续加规则，而是删掉没有产品价值的评分，只留运行底线。

# 38_怎样算好了

这个项目让我反复提醒自己：测试绿了，不等于真机通过。代码检查只能证明结构，自动化测试证明函数和协议，运行日志证明包到过。最后还要真实按键、看灯、听声音，再确认播放结束后灯真的熄灭。人的耳朵和手，仍然是最后一道验收。

# 39_还能改成什么

同一块板还可以改成很多东西，比如会议任务遥控器、工位语音信箱、设备调试台，或者家庭自动化控制台。不过我更建议从问题出发：先找一个每天都在重复、总打断你的动作，再决定它应该长成什么硬件。

# 40_复现路线图

按准备情况选择练习。没有设备可以先画输入和播放链路；有 Mac 和板子，就按教程复现，留下逐项验收记录和演示视频。视频只展示其中一段，不代替并发、断线和重启检查。跑通之后再改音色或总结侧重点，最后才考虑换任务执行器。

# 41_收束

先绑定一个测试任务，把说进去和听回来都跑通。再找一件你经常做的事，改一个小功能，记录改前和改后的差别。代码版本、操作步骤和实际结果留下来，下一次遇到问题就有依据。

# 42_附录硬件参数

附录先列公开硬件参数。主控是 ESP32-S3R8，带八兆 PSRAM，外置十六兆 Flash；有八个机械键、一个可旋转和按压的旋钮、五颗 WS2812、I2S 麦克风、数字功放和扬声器接口，同时支持 USB-C、蓝牙和二点四 GHz Wi-Fi。本案例把旋钮接成十档板载音量控制，并在固件里放入十条预生成音量提示音。

# 43_附录GPIO

这是 V2 板正面丝印和 GPIO 的最终对照。上排 S1、S2、S3、S4 分别是 GPIO2、47、38、41；下排 S5、S6、S7、S8 分别是 GPIO1、6、7、48。排查键位时要看丝印和运行诊断，不能根据最终功能猜 GPIO。

# 44_附录输入时序

当前分支由固件处理物理 PTT：按下时启动本次采集，上传带 HMAC 的 EIAU v3 音频帧，松手后发送 EIAE v3 结束帧。不是 Host 先下发 EICC start。Host 整理音频、调用 Qwen ASR，然后把文本排队，到执行时通过 stdin 交给 Codex。连接和采集身份用于隔离旧数据。

# 45_附录输出时序

Host 观察到完成事件后更新运行数，再通过心跳同步第五灯，不是零延迟。Luna High 整理总结，TTS 一次合成整段文字，缓存发布后才有信箱灯。键盘预缓冲二十四 KiB 后边收边播。只有真实播放完成且回执身份匹配，才消费这一条未读；如果已产生新总结，对应灯仍会亮。

# 46_附录安全

密钥只存在 Mac 本地的 `.env`，权限设为 0600，并由 Git 忽略。摘要状态在 Host 管理的 SQLite 中，音频加密缓存到 Mac，听完后删除。键盘只保存连接所需配置，运行时只认槽位号，不保存 Codex 对话。

# 47_附录仓库

完整工程在公开仓库 Larkspur-Wang/Codex_Keyboard。firmware 目录是 ESP-IDF 设备端，app 目录包含 Rust Host 和 Dashboard，docs 记录产品、架构、协议与开发过程。建议先按 README 跑同 Wi-Fi 演示，再深入看测试和协议。
