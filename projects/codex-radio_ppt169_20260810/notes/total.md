# 01_封面

大家好，我是 Lark。今天带来的案例叫《Codex 任务电台》。它看起来是一把八键小键盘，但我把它改成了四个 Codex 任务的实体入口：可以对任务说话，也可以直接从键盘听任务汇报。

# 02_Lark

我原来做的是嵌入式软件，日常工作离不开硬件、固件和系统边界。后来开始做 AI 产品，我没有把这些经验扔掉，而是继续问一个很朴素的问题：模型很强，但怎样才能真正进入每天的工作？这把键盘就是其中一次回答。

# 03_20秒看懂

先不讲技术，我用二十秒把结果说清楚。按住上排键，对一个 Codex 任务说要求；松开以后，Codex 在后台工作。任务完成后，对应的灯亮。再按一下下排键，键盘就把刚完成的内容读给我听。

# 04_一句话定义

一句话定义它：把四个 Codex 任务，变成四个可说、可听、会亮灯的实体频道。重点不是多做一个通知屏，也不是做一个更复杂的快捷键，而是少看一点屏幕。

# 05_真实工作桌面

这个想法来自我的真实工作。我经常同时开着几个 Codex 任务：一个改固件，一个做 App，一个跑测试，还有一个整理文档。它们都能并行，但我会不断切窗口，看谁做完了、谁在等我，注意力就这样被切碎了。

# 06_三个麻烦

我后来把麻烦归成三件事。第一，很多粗粒度要求明明说一句就够了，却必须坐回电脑前打字。第二，我总在切窗口。第三，我总想知道结果出来没有，于是本来能离开的时间，还是守在屏幕旁边。

# 07_调度瓶颈

AI 可以同时跑四个任务，人却只有一双手。真正卡住我的，不是模型写代码的速度，而是下要求、看状态、收结果这几件小事。每件事都不难，但一天做几十次，就很打断工作。

# 08_灵感瞬间

这时我手边正好有一块 EasyInput V2。它有八个键、五颗灯、麦克风、Wi-Fi、PSRAM，也留了扬声器链路。八个键刚好可以分成上下两排：上排说，下排听。于是它不再只是一把快捷键键盘，而是一个四频道任务对讲机。

# 09_四个频道

我用了对讲机这个比喻，因为它很容易理解。四个任务就是四个频道。对哪个频道说，要求就进入哪个任务；哪个频道有回信，就亮哪颗灯；想听哪个频道，就按对应的下排键。

# 10_交互草图

这是最初的交互草图，主体没有变。S1 到 S4 负责按住说话，S5 到 S8 负责收听。左起四颗灯一一对应四个语音信箱，最右第五颗单独显示后台有几个任务正在跑。旋钮也没有闲着：逆时针调小键盘扬声器，顺时针调大，短按一下还会直接告诉我现在是百分之多少。

# 11_开发板本质

EasyInput 出厂时可以直接当 AI 键盘使用，但它的本质是一块开发板。键位和旋钮只是已经做好的一个形态。真正有意思的是，你可以重新定义这块板怎样感知人、怎样和电脑协作、怎样给反馈。

# 12_用人话认识硬件

不用先记芯片型号，先用人话认识它。八个机械键让它能按，旋钮直接调键盘自己的播报音量，I2S 麦克风让它能听，功放和扬声器让它能说，五颗 RGB 灯让它安静地提示状态。音量做成十档，逆时针减、顺时针加；短按旋钮，键盘会直接播报当前档位。

# 13_激活能力

这次案例真正用上了几项原来没有完整跑起来的能力。PSRAM 用来放音频缓冲，Wi-Fi 负责传声音，数字功放和扬声器负责把总结播出来。也就是说，我们不是只改键位配置，而是把整条音频链路做进了固件。

# 14_本地WiFi

第一版我先选择同一个局域网。键盘和 Mac 连到同一个 Wi-Fi，声音和状态都直接走本地链路。这样问题更容易定位，数据也更可控。标题里的“远程开发”，指的是人可以离开 Codex 窗口继续工作，不是说当前版本已经能从公网遥控家里的 Mac。

# 15_MacApp绑定

Mac App 是这套系统的管家。它把四个槽分别绑定到四个 Codex 任务，也显示哪些槽有未听汇报、键盘是否在线。这里展示的是实际界面，任务名称已经换成课程示例。底层数据库只由 Host 管理，界面通过 Host 读取状态，避免两边同时改数据。

# 16_按住说

输入动作很简单。按住 S1 到 S4 中的一个键，键盘开始录音；直接说要求；松开以后结束录音。Mac 调用千问 ASR 把语音转成文字，再把文字排进对应 Codex 任务的队列里。

# 17_后台工作

最有价值的动作其实是“发完就走”。我不需要看进度条，也不用等一段命令跑完。Codex 在后台做事，我可以去处理别的工作。只有任务真的完成，系统才来提醒我。

# 18_语音信箱灯

五颗灯现在分成两种职责。左起四颗仍然是四个语音信箱：哪个任务完成了，对应槽位就亮，未听内容越多越亮。最右第五颗只看后台忙碌程度：空闲是绿色，一个任务黄色，两个橙色，三个紫色，四个红色；全部完成后再回到绿色。为了让紫色和红色不是只画在图上，Host 允许四个不同任务同时运行；但同一个任务仍然排队，避免同一段对话同时写入。这样一眼就能分清“还有多少任务在跑”和“哪些结果还没听”。

# 19_收听映射

上下两排是一一配对的。S1 负责给槽一说话，S5 负责听槽一；S2 对 S6，S3 对 S7，S4 对 S8。按一下下排键，就播放那个槽提前生成好的音频，不需要再临时等待总结。

# 20_总架构

整套架构可以不用协议名来解释。键盘是身体，负责收声音、亮五颗灯、播声音；Mac 是管家，负责绑定任务、数清正在运行的任务、总结和缓存；Codex 是执行者，真正写代码、改文件、跑测试。第五灯的颜色不是固件猜出来的，而是 Mac 观察任务开始和完成以后告诉键盘的。

# 21_原理基础篇

接下来这一章，是专门给硬件小白的原理基础课。十张概念卡，每张用一个比喻讲透一个词。这些不是为了考试，而是你复现时每一步背后的「为什么」。现在快速过一遍建立地图，回去跟教程动手时看不懂名词，就回这一章查。

# 22_局域网直连

第一张卡，局域网直连。键盘和 Mac 在同一个 Wi-Fi 里直接说话，就像同一栋楼里的两个人，喊一声就能听见；用云中转就像各自打电话给国外客服，再让客服互相转达。我们用 UDP 直发 Mac 的 17333 端口——对讲这种场景丢一帧没关系，慢了才难受。WebSocket 建立在 TCP 上，要维持长连接、会卡顿重传，对单片机太重。附带好处：断了外网照常用，录音不经过任何第三方。注意宿舍和公司 Wi-Fi 常开 AP 隔离，测试用家用路由器或手机热点最稳。

# 23_配网

第二张卡，配网。键盘没有屏幕和输入法，Wi-Fi 密码怎么进去？像给新员工发工牌：provision-lan 命令通过 USB（不通就走蓝牙）把四样东西一次写进键盘——SSID 和密码、Mac 的 IP、端口，还有一把叫 device secret 的钥匙。一次配好，之后开机自动连。一个安全细节：密码只走标准输入，不写在命令行参数里，免得留在 shell 历史。

# 24_Flash分区与NVS

第三张卡解释一件很多同学会惊讶的事：重刷固件，配置居然还在。因为键盘的 16 MB 存储被分成了几个抽屉，烧录只写 bootloader、分区表、应用程序三个抽屉；NVS 这个保险柜抽屉存着 Wi-Fi、密钥和音量档位，动都不动。所以千万别自己加 erase_flash 整片擦除，那会把保险柜和开机音一起清掉。

# 25_声音变数字

讲链路之前，先补一个基础：声音是怎么变成数字的。可以想成给声音拍连拍照片：每秒拍一万六千张，每张用十六位记录，这就是 16 kHz 的 PCM16。上行像直播，边说边传给 Mac；下行是 TTS 先合成高音质音频，Host 压缩、加密、缓存好，等你按键再播。记一个排错口诀：声音变调，八成是两端采样率没对上。

# 26_认证与加密

第五张卡，认证与加密。有人问：都在自己家 Wi-Fi 了还防谁？答案是局域网不等于可信网，里面可能还有别人的设备。两层防护：控制包带 HMAC 防伪签名，验不过直接丢；语音用 AES-256-GCM 上锁，抓包只能看到密文。钥匙就是配网时发进键盘的 device secret。记住这个系统的脾气：验证失败一律静默丢弃，不猜、不放行，也不会给你报错。

# 27_代际

第六张卡，代际，就是取餐号。餐厅换班重新叫号，旧小票就作废了。总结每发布一版就有一个新 generation，键盘断线重连后，旧代的音频缓存和播放请求全部失效——你听到的永远是最新一版，把昨天抓的包今天重放也没用。调试时看到「包发了对方不理」，先查代际是不是翻新了，这是设计，不是 bug。

# 28_FIFO排队

第七张卡，FIFO 排队。想象银行四个窗口：每个窗口前一条队，队内先来先办，窗口之间互不影响。对同一个槽连说三条要求，它们排队按序执行——Codex 任务有上下文，乱序会搞乱；但其他槽完全并行。第五颗灯的颜色就是「几个窗口正在办业务」。对同一个槽觉得没反应，多半是前一条还在跑。

# 29_任务完成

第八张卡回答「什么才算完成」。标准只有一个：Codex 自己在 rollout 日志里写下 task_complete——像快递以系统里的签收记录为准，不以快递车开走为准。Host 看到这个权威事件才开始动作：让 luna 写十五秒口播稿、TTS 合成、加密缓存、点亮信箱灯，没听的旧总结滚进新一版一起说。失败、超时、取消都不点灯——灯不亮先去 App 看任务状态。

# 30_听过语义

第九张卡，什么才算「听过」。必须扬声器物理播放到最后一个采样点，键盘带着代际号回执，Host 核对无误才删缓存、熄灯。键盘会先把整段音频装进 PSRAM 再开始播，Wi-Fi 抖动也不断音。播放中按住 PTT 会立刻让位——PTT 永远优先，这条总结仍算未听，下次还能听。中途拔电灯常亮，是特性不是 bug：没听完就不算听过。

# 31_常驻管家

第十张卡，常驻管家。真正干活的是 easy-codex-host，安装成 macOS 开机自启的 LaunchAgent；四个槽绑了哪些任务、每个槽的队列、未读总结和代际、音频缓存，全归它管，存在 SQLite 里。键盘和桌面 App 都只是它的客户端——这就是「状态必须有唯一所有者」。所以升级 Host 要用 launch-agent-upgrade 换掉管家本人，光重启 App 没用。十张卡讲完了，接下来看这些概念怎么串成两条完整链路。

# 32_说进去

语音输入这条链是这样的。键盘采集十六千赫兹单声道 PCM，通过局域网送到 Mac。Mac 调用北京区 DashScope 的千问语音识别，把声音变成文字，再把文字放进绑定任务。键盘不需要理解内容，它只要把声音可靠送到就行。

# 33_Spark总结

任务完成以后，Host 读取助手最后的回复，再交给隔离运行的 Codex Luna High 提炼。这里我限制的是来源：只看真正完成时的助手回复，不把调试过程、工具日志和中间想法念出来。短结果就说一句，复杂结果才多讲。实践中我也踩过一个坑：给总结加太多字数、证据和内容评分，反而会把本来能听的结果挡住。现在质量交给 Luna，Host 只守结构、任务归属、长度、脱敏和有效音频这些运行底线。

# 34_听回来

总结完成后，Mac 把整段文字一次交给千问 Audio 3.0 TTS Flash，用龙安风玥女声生成一条完整音频，再加密缓存到本地，不做分句拼接。按下播放键后，键盘通过局域网取回对应音频，再交给 I2S 扬声器播放。音频早在任务完成时就已经生成，所以按键不是临时等云端合成。

# 35_抽取工程

这个案例不是在原键盘仓库里不断加特殊代码。我先从成熟的 EasyInput 固件基线中，抽出本地 Wi-Fi 版本需要的部分，建立独立的 Codex_Keyboard 仓库。里面明确分成 firmware 和 app，两边的边界、协议和测试都单独记录，原仓库保持不动。

# 36_第一次卡住

开发过程并不顺。第一个问题是下载模式很难进，串口设备只在上电瞬间出现。最后固定的方法是先用 debug reset 拉住，再抓断电上电的瞬间。另一个问题更迷惑：有开机音，却没有任务音频。开机音只证明扬声器能响，不能证明网络、缓存和解码都通，所以必须逐段排查。

# 37_隐蔽问题

后来还有三类更隐蔽的问题。传输窗口大过设备的 UDP 接收队列，导致丢包和重传，听起来就是每次都很慢。灯带在 PCB 正面看是从左到右，但数据链路方向相反，所以灯序一开始完全反了。最后一个问题最值得讲：任务和总结其实都完成了，S7 却不亮，因为我给 Luna 输出叠了太多自以为安全的内容门禁。解决办法不是继续加规则，而是删掉没有产品价值的评分，只留运行底线。

# 38_怎样算好了

这个项目让我反复提醒自己：测试绿了，不等于真机通过。代码检查只能证明结构，自动化测试证明函数和协议，运行日志证明包到过。最后还要真实按键、看灯、听声音，再确认播放结束后灯真的熄灭。人的耳朵和手，仍然是最后一道验收。

# 39_还能改成什么

同一块板还可以改成很多东西，比如会议任务遥控器、工位语音信箱、设备调试台，或者家庭自动化控制台。不过我更建议从问题出发：先找一个每天都在重复、总打断你的动作，再决定它应该长成什么硬件。

# 40_复现路线图

最后给大家一条明确的回家路线，四级作业，每一级都算数。L0 不需要板子，把「说进去、听回来」两条链路画出来、标出真相源，就算完成；L1 是按飞书教程把整套系统跑通，过完七条验收，交三十秒真机视频；L2 改参数，比如换音色、改总结时长、换灯的配色；L3 改语义，设计你自己的第五灯，甚至换掉执行器。手把手教程已经发到飞书，概念卡、全部命令和验收表都在里面。

# 41_收束

最后我想留下一个很具体的认识。AI 硬件不是把大模型塞进 ESP32，而是给 AI 一副能进入日常工作的身体。它能听见要求，安静地等结果，再用灯和声音把重要的事带回来。这就是 Codex 任务电台。

# 42_附录硬件参数

附录先列公开硬件参数。主控是 ESP32-S3R8，带八兆 PSRAM，外置十六兆 Flash；有八个机械键、一个可旋转和按压的旋钮、五颗 WS2812、I2S 麦克风、数字功放和扬声器接口，同时支持 USB-C、蓝牙和二点四 GHz Wi-Fi。本案例把旋钮接成十档板载音量控制，并在固件里放入十条预生成音量提示音。

# 43_附录GPIO

这是 V2 板正面丝印和 GPIO 的最终对照。上排 S1、S2、S3、S4 分别是 GPIO2、47、38、41；下排 S5、S6、S7、S8 分别是 GPIO1、6、7、48。排查键位时要看丝印和运行诊断，不能根据最终功能猜 GPIO。

# 44_附录输入时序

完整输入时序从按键按下开始。Host 发出开始采集控制，键盘持续上传 EIAU 音频帧；松开后结束并整理音频。Host 调用 Qwen ASR，拿到文本，再写进对应任务的 FIFO。每一步都有明确的会话代际，避免旧连接的数据混进新录音。

# 45_附录输出时序

输出侧从 Codex 完成事件开始。Host 先把正在运行的任务数减一，所以最后一个任务完成时，第五灯立即回到绿色；随后 Luna High 整理可听总结，Host 把完整文本一次交给 Qwen Audio 3.0 TTS Flash 生成音频并缓存，对应的信箱灯再亮起来。播放时，传输完成和扬声器完成分开记录；只有扬声器完成，才标记 heard、熄灭对应信箱灯并删除缓存。

# 46_附录安全

密钥只存在 Mac 本地的 `.env`，权限设为 0600，并由 Git 忽略。摘要状态在 Host 管理的 SQLite 中，音频加密缓存到 Mac，听完后删除。键盘只保存连接所需配置，运行时只认槽位号，不保存 Codex 对话。

# 47_附录仓库

完整工程在公开仓库 Larkspur-Wang/Codex_Keyboard。firmware 目录是 ESP-IDF 设备端，app 目录包含 Rust Host 和 Dashboard，docs 记录产品、架构、协议与开发过程。建议先按 README 跑同 Wi-Fi 演示，再深入看测试和协议。
